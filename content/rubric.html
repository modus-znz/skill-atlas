Scoring rubric

How every score in the report was computed.

No skill was scored by hand. A hand-assigned number across the whole library would be unverifiable and inconsistent, so the score is a formula over measured properties — which means you can disagree with the weights and recompute, rather than having to take the number on trust. Six dimensions, 100 points.

The bands above are read from config/rubric.json at render time rather than restated here, so this table cannot describe a rubric the report is not actually using. Edit that file and this follows.

  • Reachability — a skill the model cannot select is not capability. This is the single strongest predictor of whether a skill ever fires, and it is weighted accordingly.
  • Description quality — search ranks on the description, and for hidden and vault skills it is the only route in. Too short is unfindable; too long is a standing tax when listed.
  • Bundle depth — a references/, scripts/ or assets/ directory is the difference between a skill and a note-to-self, and it is what makes progressive disclosure possible at all.
  • Body weight — a skill has to be loadable without eating the window. This band is a curve, not a floor: thin loses to good, and very long loses again, because a forty-thousand-character single file is a real cost. A low score here is ambiguous between too short and too long, and only one of those is a defect.
  • Freshness — newest file mtime in the bundle. A proxy, not proof, but a skill untouched for a year in a fast-moving toolchain is a different risk from one touched last week.
  • Hygiene — duplicate cached copies and name collisions have real consequences: one costs disk and resolution ambiguity, the other costs reachability outright.

Grade bands

  • A 82–100 — reachable, well-described, properly bundled. {{ metrics.grade_a }} skills.
  • B 70–81 — sound, with one weak dimension. {{ metrics.grade_b }} skills.
  • C 58–69 — a real defect worth fixing. {{ metrics.grade_c }} skills.
  • D 45–57 — two or more compounding defects. {{ metrics.grade_d }} skills, of which {{ metrics.grade_d_billed }} are billed in the listing.

What the score deliberately does not measure

  • Quality of the instructions. Judged only by proxy — nothing here reads the prose and rates the advice.
  • Fit to this machine's work. Handled separately in the density verdicts, which are hand-authored at the category level.
  • Actual usage. No invocation telemetry is available, so a brilliant skill never once fired scores identically to one used daily.

Treat a score as a triage signal — where to look first — not a verdict.

Method

  • Walked four roots, parsing YAML frontmatter from every SKILL.md — and, in the flat ~/.claude/agents root, from every <slug>.md carrying a name: key. Symlinks not followed, .git and node_modules excluded. {{ metrics.files_scanned }} files.
  • Collapsed the plugin cache to the newest version per (plugin, skill) — semver preferred, mtime as the tiebreak for hash-named directories. {{ metrics.stale_copies }} superseded copies removed → {{ metrics.total }}.
  • Reachability derived from skillOverrides and enabledPlugins in ~/.claude/settings.json, not from documentation.
  • Token figures are estimates at chars ÷ 3.6. Good to roughly ±10% for English prose with code fences; treat them as comparative, not exact.
  • Upstream figures fetched live from the public repositories on the generation date.
