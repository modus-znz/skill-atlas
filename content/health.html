Health & findings

The failure modes this census looks for, and where each one shows up.

Credentials in build configuration

Not machine-checkableSecurity

The most serious problem a skill library audit can find is usually not a library problem at all, and no filesystem scan will surface it. The recurring shape is a release signing config — Android, iOS, package signing — that declares the store and key passwords inline in a tracked build file, with the keystore itself committed. The reason it survives review is that a .gitignore rule for the key file exists and looks like it handles the case. It does not: gitignore never applies to a file that is already tracked. The rule is inert, and anyone with read access can produce a build the platform accepts as genuine.

Fix, and deleting the files is not enough. Anything committed must be treated as compromised and rotated: generate a new key and re-key, then either purge history or move to the platform's own upload-key indirection where one exists. Afterwards, read the credentials from an untracked local properties file at build time. Note the asymmetry: rotation fixes the forward path, history rewriting fixes the past, and neither substitutes for the other.

An always-loaded skill is the most expensive file in the tree

MeasuredContext cost

Instructions that tell the model to load a skill “at the start of any non-trivial task” make that skill's entire body a fixed tax on every request. If it is a large file, it may be paid several times per session, and the cost lands hardest in exactly the sessions that are already long. A skill can be excellent in every respect and still be a bad citizen purely on body weight.

Fix: progressive disclosure. Keep a small core — decision order, the name index the reader needs to navigate, a threshold table — as the always-load entry point, and move the derivations, runbook index and inventories into references/ files the core points at by name. Verify conservation mechanically: set-difference the identifiers in the old file against core-plus-references so a split cannot quietly drop a capability. If a core cannot be made small because the two sections that make it worth loading are themselves large, that is a legitimate outcome — record it rather than cutting something useful to hit a byte target.

Descriptions too short for the search that has to find them

MeasuredDiscoverability

Search ranks on the description string, so a short description is a discoverability defect, not a style one. It bites hardest on skills that are not in the session listing, because for those the description is the only thing search has to match against. A few dozen characters gives the ranker almost nothing, and the skill loses to longer, vaguer entries on queries it should win outright. A length floor will catch the genuinely empty ones; it will not catch the merely unhelpful, which need reading.

Fix: extend each to roughly 150–300 characters carrying real trigger vocabulary — model names, file types, path fragments, error strings, API symbols — the things a real query would contain. Check whether the skill is re-listed anywhere project-scoped before claiming the change is free: a per-project settings file can re-list it and make the longer text a real cost in that one repository.

Colliding names, and shadow events that are phantoms

MeasuredReachability

When an index keeps one winner per id under a precedence order, every losing copy is unreachable — and, if search iterates the winners-only map, unreachable by any spelling, not merely by load. Ties then break on filesystem enumeration order, so which copy survives is not a policy decision at all. The subtle half is the false positive: a collection that symlinks one directory to another makes a walker that only dedupes entries reached through a symlink walk the same files twice, so each skill shadows itself. The tell is a file count that disagrees with the skill count.

Fix, two independent changes: namespace ids as collection/name, letting a bare name still resolve to the highest-precedence copy and report its siblings as variants so choosing one is deliberate rather than silent; and dedupe on the realpath of every directory entered, not just of symlinked entries. The second is a couple of lines and removes the phantom reports on its own.

Duplicate copies that do not sort

MeasuredHygiene

Semver-named version folders sort, so the newest is determinable. Content-hash-named folders do not, so the current copy has to be resolved by modification time — which means a stale copy can win if a file is ever touched. Several copies of one unit is genuinely fragile resolution. It is also frequently not where the disk went: a handful of hash directories may be megabytes in total while the weight sits in a different plugin that vendors a browser or a dependency tree. Measure bytes directly rather than counting directories, and be prepared for the directory count to point somewhere else entirely.

Fix: keep the one version each manifest entry actually resolves to and remove the rest. Resolve the keeper from the installed-plugin manifest rather than from the tree, assert it exists and is non-empty before deleting anything, and re-verify every plugin resolves afterwards.

A rubric that penalises a cost the skill cannot incur

Open by decisionMeasurement

This one is about the measurement, not the library, and it is worth reading carefully because it is the failure mode that makes an audit actively misleading. {{ metrics.desc_bloated }} skills lose points for running past rubric.desc.long_max. {{ metrics.desc_bloated_billed }} of them are billed — each sits in the vault, a disabled plugin, or an unset plugin, where description length is charged to no session prefix. The penalty is calibrated for the listing and then applied uniformly, so it measures a cost these skills structurally cannot pay.

Worse, it points the wrong way: search weights a description match per query token, so on an unbilled skill a longer description is a pure retrieval gain. Acting on the score would make {{ metrics.desc_bloated }} skills harder to find and save nothing. This is also the whole of the remaining grade-D population: {{ metrics.grade_d }} D-grade skills, {{ metrics.grade_d_billed }} of them billed.

Fix: make the desc band reach-aware — charge length only where the listing bills it. Deliberately not done here, for a reason worth copying: rubric.json records that its weights are held steady so scores stay comparable with an earlier baseline, and re-banding silently re-scores every skill in the library, including any finding that cites a grade. Re-baselining is a decision to take deliberately, not a side effect of a cleanup.

One collection vendoring byte-identical copies of its own skills

Open by decisionTidy-up

Distinct from superseded cache versions: these are same-version fan-out inside a single upstream repository, where one skill is committed once per sub-directory it is relevant to and the copies share an identical checksum. It looks like local duplication and is not — it costs no listing tokens, and once ids are qualified every copy is separately addressable. Worth recording so the repeated names are not mistaken for a mistake to fix locally.

Fix: none locally. It is upstream vendoring. Recorded, not chased.

Two generations of the same skill installed side by side

Open by decisionTidy-up

A -v1 left beside its successor, or a family of near-synonymous names that drifted apart, makes the router's job harder and leaves you maintaining both. Retiring a listed skill returns its description from every session, which is a real but modest saving, and it is a judgement call about which implementation you trust rather than a token argument.

Fix: pick a winner per pair and delete or move the loser to the vault.

Frontmatter that fell out of the block

MeasuredParse hygiene

The quietest failure in the set, and the most worth a check. A well-written description can end up stranded in the body of a file instead of inside --- — usually after a bulk import. It is quiet by construction: a parser that falls back to the first non-heading body line will then return the literal text description: Track and… as if it were the description, so search returns a plausible-looking snippet while the real text was never indexed, and the label itself now pollutes the haystack it is being searched in.

Fix: hoist descriptions into real YAML frontmatter, preferring the folded block-scalar form because it survives the colons, quotes and indentation these texts tend to contain. Then verify through two independent parsers and count how many units still rely on the fallback.
