Family density

Whether a small category is a gap worth filling or a domain that is simply finished.

The active library sorts into eleven families, and five of them hold six skills or fewer. The obvious reading — thin means missing — turns out to be wrong for four of the five. What actually separates a healthy small family from a gap is not the count but the spread: how far apart the best and worst member score. A family with four skills and a twelve-point spread is being measured. A family with sixty-two skills and a spread of zero is not.

Thin by count, dense by quality — four of the five need nothing

Video production (4 skills, avg 90.5, all A), Motion & animation (6, avg 89.3, all A), Editor & model tooling (4, avg 83.0) and Writing & documents (6, avg 85.7) are small because their domains are small, not because coverage is short. Editor tooling is the clearest case: it is bounded by how many host editors exist, so it can only grow when a new editor does. Adding skills to any of these four would add listing weight and no capability. No action

Build & release looked like the real gap. It was a discovery problem.

One skill, and the first instinct was to go shopping upstream. That instinct was wrong, and it is worth recording why: the vault already holds devops/release/semantic-versioning (MIT, 477 lines — SemVer, conventional commits, semantic-release, GitHub Actions release workflows), plus changelog-generator, git-workflow-and-versioning, feature-flags, blue-green-deploy and five sigstore/SBOM/cosign supply-chain skills. Every one of them wins its own skill_search. The coverage was never missing; nothing pointed at it.

So the fix is a pointer, not an acquisition. Fixed 2026-09-06 A routing bullet now sits in claude-router's decision list with the detail in references/skill-vault.md §Release engineering. Promoting semantic-versioning to listed was considered and rejected on measurement: a vault skill costs 0 listing tokens and is already fully reachable via skill_search/skill_load, so a copy in ~/.claude/skills/ would buy no reach and cost a name collision (−3 hygiene, one shadowed entry).

One genuine gap survives the audit: monorepo release orchestration — changesets, lerna, nx, turborepo — verified absent across the entire vault (zero keyword hits, 2026-09-06). It is worth acquiring when a monorepo actually needs releasing, and not before. API deprecation mechanics (sunset headers, version negotiation, migration windows) are thin, though the doctrine behind them is already solid in api-and-interface-design.

Design aesthetics: 62 skills, every one scoring exactly 81

This is the strongest finding on the page, and it is about the rubric rather than the skills. Design aesthetics is 42% of the active library and its score spread is zero — every member scores 81, with identical parts (reach 16 · desc 25 · depth 5 · body 15 · fresh 10 · hygiene 10). The mechanism is now confirmed in atlas/score.py: five of the six dimensions saturate for all 62, and depth sits uniformly at base = 5 because every one of them has more than one file and none has a qualifying subdirectory. A rubric that returns a constant over the largest family has stopped ranking inside it — the grade is noise wearing the costume of a signal.

Detected 2026-09-06 atlas.py doctor now reports any family of ten or more with zero score variance as a notice. Deliberately a notice and deliberately additive: retuning the weights to break the tie would change every score in the report and break comparability with the 2026-09-04 baseline that atlas.py diff measures against. The check fires on exactly one family today — Build & release also has a spread of zero, but at n=1 that is arithmetic, not a blind spot, which is why the threshold is n ≥ 10.

What would actually fix it, when comparability is worth spending: these are aesthetic systems, so the dimension that would separate them is whether a skill ships something executable — a token file, a component sample, a reference page — rather than prose alone. That is a new dimension, not a re-weighting of an existing one, and it belongs in a deliberate rubric v2 with a fresh baseline rather than a quiet edit to config/rubric.json.

Five listed skills carried their whole manual on every invocation

The audit's other correction ran the opposite way. body is a bell curve, not a floor — thin <400 = 4, good = 15, long = 10, bloated >25,000 = 5 — so a low body score is ambiguous between too short and too long, and these five were far too long: single-file SKILL.md documents of 27,000–40,000 characters, all of them listed, all scoring B78 on the identical fingerprint depth 3 + body 5.

Fixed 2026-09-06 All five were split on their existing ## boundaries into a lean SKILL.md plus a references/ bundle — the standard progressive-disclosure pattern from the Agent Skills spec. The splitter asserts that every source ## section lands somewhere exactly once, so the mechanical part is guaranteed lossless. Two hand-edits sit outside that assertion, both on imagegen-frontend-mobile: its preamble repeated the anti-AI-tells list that §21 already owns, so the duplicate was replaced by a pointer naming §21 and the eight positive rules that carry the rest of it. One canonical list, checked by hand against the backup — not a trim bought for the score.
